## Abstract

This RFC sets how languages are handled in the CTF standard. Requirements describe behaviours and do not depend on a language; they are published in English and French, English being authoritative. Scenarios, on the other hand, are measurement instruments, and an instrument is only valid in the language and country it was validated for. This RFC therefore introduces the **locale** (language + country, for example `fr-FR`) as the unit of validation: each scenario has one language-independent specification and one version per locale, each locale version is validated on its own, and every result is valid only for the locale it was obtained in.

## Motivation

CTF documentation is bilingual, but a test is always run, and judged, in one particular language. Three observations show that a result obtained in one language cannot be assumed to hold in another:

1. **Agents do not behave the same way in every language.** The safety behaviour of language models is known to be weaker in some languages than in English. An agent may name the right crisis resource in French and miss it in English, or the reverse.
2. **A scenario cannot simply be translated.** Several requirements rely on signals carried by idioms. Softened distress signals, which RFC 0008 places under R3 ("just for a moment", "but it's nothing"), are a good example: a literal translation can make the signal stronger or weaker, and the test then no longer measures the same thing. Adapting tests across languages is a known problem in psychology and education, with established practice (translation, back-translation, expert review, pilot).
3. **Model evaluators do not judge equally well in every language.** Agreement between evaluators has to be measured language by language.

A fourth observation concerns the country rather than the language: the correct crisis resource is not the same in France, Switzerland, Belgium or Quebec, although the language is the same.

Without an explicit rule, a report could present a verdict obtained in one language as if it applied to the agent in general. This RFC prevents that.

## Detailed proposal

### 1. Definitions

- **Locale:** a language and a country, written as a BCP 47 tag: `fr-FR`, `fr-CH`, `en-GB`, `en-US`…
- **Normative text:** the requirements, the evaluation protocol and the evaluation criteria.
- **Scenario specification:** the language-independent description of a scenario: identifier, requirement(s) tested, intent of the stimulus, what makes it a signal, expected behaviour, level of difficulty.
- **Locale version of a scenario:** the concrete form of a scenario in one locale: the triggering message, word for word; the brief given to the simulated client; references to locale-specific data.
- **Locale-specific data:** reference data that depend on the country, such as the list of crisis resources.

### 2. What is fixed and what is free

| Level | Depends on language? | Rule |
|---|---|---|
| Requirement | No | One normative text, published in English and French; English is authoritative |
| Scenario specification | No | One text, one identifier independent of the language |
| Locale version of a scenario | Yes | Fixed for each locale. Each locale version is a separate instrument with its own status |
| Rest of the conversation | Yes | Free, generated by the simulated client in the language of the locale |
| Evaluation criteria | No | Common texts; citations stay in the language of the conversation |
| Locale-specific data | Country | One reference list per country, versioned with the standard, checked without model judgement where possible |
| Result | Yes | Valid for the agent as observed at one address between two dates × one standard version × one locale (RFC 0010, section 2) |

### 3. Normative texts

Requirements and the evaluation protocol are published in English and French. English is authoritative in case of divergence. Translating a normative text is an editorial task: it is reviewed for accuracy but does not need empirical validation, because it does not change what the test measures.

### 4. Scenarios: adapted, not translated

A locale version is written either directly in its language or adapted from another locale version. An adaptation may change the wording, the idioms and the cultural details, provided that the stimulus keeps the same nature and the same strength as stated in the scenario specification. Literal translation is not a goal.

### 5. Validation of a locale version

A locale version has a status: `draft`, `validated` or `retired`. It becomes `validated` when the four conditions below are met and recorded:

1. **Expert review.** At least one coach who is a native speaker of the locale's language has reviewed the locale version against the scenario specification. When the version is adapted from another locale, a back-translation is attached to the review.
2. **Stimulus check.** In pilot runs, the simulated client actually delivers the triggering message in that language. A run where the stimulus was not delivered gives `not_observed`, never a pass.
3. **Pilot on the reference agents.** The compliant reference agent passes and the defective reference agent fails where its defects are documented. This is the simple check that the test measures the same thing from one locale to another.
4. **Evaluator agreement.** Agreement between model evaluators and human reviewers is measured in that language, following RFC 0010, section 11.

The names of the reviewers, the dates and the pilot results are kept in the record of the locale version.

### 6. Locale-specific data

Data that depend on the country, such as crisis resources, are kept in the standard as versioned reference lists, one per country. A scenario that relies on such data states the person's country in its locale version (for example "I live in Lyon"), so that the expected answer is defined. Where possible, the check is deterministic (is the number given by the agent in the reference list?) rather than left to a model evaluator.

### 7. Results and reports

- Every run records its locale.
- A verdict is valid only for the locale it was obtained in. It is never extended to another locale.
- Reports give verdicts only for validated locale versions. Results from locale versions in `draft` status are shown as **exploratory** and do not count in the verdicts.
- Results from several locales may be shown side by side, but are never merged into a single verdict.

### 8. Language of the agent's reply

What a requirement asks the agent to communicate (that it is an AI, the request for consent, the crisis resource…) must be given in the language of the person. A disclosure or a resource given in another language than the person's does not satisfy the requirement. RFC 0010, section 8, proposes that such a reply count as a failure of the criteria that ask the agent to do something (see open questions).

### 9. Application to version 0

Version 0 of the standard (RFC 0008) is validated for the `fr-FR` locale only. Its scenarios are written in French first. Other locales will be added later, following this RFC.

### 10. Out of scope for now

A person who changes language during the conversation, and multilingual persons, are not covered. They are good candidates for robustness scenarios in a later version.

## Empirical evidence

No evidence-log entry is cited yet. The proposal relies on:

- published work on the safety of language models across languages:
  - Z.-X. Yong, C. Menghini and S. H. Bach, *Low-Resource Languages Jailbreak GPT-4*, NeurIPS 2023 workshop (SoLaR), [arXiv:2310.02446](https://arxiv.org/abs/2310.02446). Translating unsafe requests into low-resource languages with machine translation was enough to bypass GPT-4's safeguards in a large share of cases; the authors conclude that safety training generalises poorly across languages.
  - Y. Deng, W. Zhang, S. J. Pan and L. Bing, *Multilingual Jailbreak Challenges in Large Language Models*, ICLR 2024, [arXiv:2310.06474](https://arxiv.org/abs/2310.06474). Without any malicious intent, low-resource languages produced about three times as much unsafe content as high-resource languages, for ChatGPT and GPT-4.
- established practice for adapting tests across languages and cultures: International Test Commission, *ITC Guidelines for Translating and Adapting Tests* (second edition), 2017, *International Journal of Testing*, [doi:10.1080/15305058.2017.1398166](https://doi.org/10.1080/15305058.2017.1398166). Eighteen guidelines in six groups (pre-condition, test development, confirmation, administration, scoring and interpretation, documentation). Sections 4 and 5 of this RFC follow their logic: adaptation rather than literal translation, then empirical confirmation of equivalence.

**Limits of this evidence.** Both model studies measure general harmful requests, not coaching conversations, and their contrast is between high-resource and low-resource languages. Neither studies French: French and English are both high-resource languages, so these studies do not show a gap between them. They show that safety behaviour *can* depend on the language, which is enough to forbid assuming that it does not; they do not measure the size of the effect for the locales CTF will use first. Evidence specific to coaching agents, and to French versus English, will come from the first runs of ctf-test in more than one locale.

## Impact analysis

### On adopters

An agent offered in several languages must be tested in each locale for which a result is claimed. The cost of testing grows with the number of locales.

### On the reference testing tool (ctf-test)

The tool stores the locale of every scenario version and every run, keeps the validation record of each locale version, separates exploratory results from verdicts in reports, and never merges verdicts across locales.

### On the reserved test set (RFC 0005)

A reserved set, if adopted, is also kept per locale.

## Alternatives considered

- **Validate scenarios once, in English, and translate them.** Rejected: it assumes that agents, signals and evaluators behave the same in every language, which the observations above contradict.
- **Let the simulated client speak any language freely.** Rejected: the stimulus would no longer be controlled.
- **Record the language as information only, without validation per locale.** Rejected: reports would present results from unvalidated instruments as verdicts.
- **Use the language alone (`fr`) rather than the locale (`fr-FR`).** Rejected: country-specific data, such as crisis resources, would be undefined.

## Open questions

1. **Language of the evaluation instructions.** Are the instructions given to model evaluators written once, in English, whatever the language of the conversation, or translated into that language? Default proposed: written once, in English; to be checked during evaluator calibration.
2. **Derived locales.** Can a locale with the same language but another country (for example `fr-CH` from `fr-FR`) be validated with a lighter procedure: review of the locale-specific data and the idioms, then a pilot, without a full adaptation?
3. **Qualification of reviewers.** Which qualification is required to review a locale version (native speaker, practising coach, credential)?
4. **Size of the pilot.** How many runs on the reference agents are needed before a locale version is validated?
5. **Reply in another language (section 8).** Should a reply in another language than the person's count as a failure, or as `not_observed`? Proposed answer: a failure (RFC 0010, section 8).
